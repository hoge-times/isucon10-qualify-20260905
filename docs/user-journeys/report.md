# ISUUMO：ブラウザで確かめたユーザーストーリーと加点動作

2026-09-05 / 対象：[練習環境](http://54.168.109.155/) / 2回の試行（trial-01、trial-02）の統合レポート

**イス購入に至る2経路、物件の資料請求に至る4経路の計6経路をブラウザで実行し、購入2回・資料請求4回のすべてで画面に200が表示された。直接加点に対応するのは、検索の成功ではなく、この購入・資料請求の送信成功である。** あわせて「検索結果がなくなったら条件を緩める」「メール入力を修正して再送する」という復帰の流れも確認した。

ブラウザでの手動操作はベンチマーカーのスコア計測ではない。採点仕様上、ベンチ走行中に同種の成功が計上され減点が増えなければ、購入2件＋資料請求4件は合計6点に相当するが、**手動操作でスコアが6点増加したという測定結果ではない**。

## 仕様の理解

ISUUMOは「イスに似合う不動産を検索できる」サービス。イスを購入する利用と、転居先の物件資料を請求する利用があり、イス詳細のおすすめ物件が両者をつなぐ。

マニュアルの採点式は `スコア = (イスの購入件数 + 物件の資料請求件数) - 減点`。ベンチはAPIのみを呼び、HTML・画像の取得は行わない。ただしブラウザ表示は追試対象となる。

補足：

- US-01のイスは名前ではなく詳細の種類欄で検索条件との一致を確認した。検索結果はページを送ると別の候補に変わった。

- US-03の条件検索の2件は48347円→45672円の順で、価格昇順ではなかった。「検索結果の先頭＝最安」とは判断できず、最安一覧と条件検索は利用上の役割が異なる。

## 動作とAPIの対応

API名は手元のfrontend・Go実装から照合したもの。実ブラウザのネットワークログを採取した結果ではない。

### 経路ごとの処理

| 経路 | 加点前の主な処理 | 加点対象の処理 |
|---|---|---|
| イス条件検索（US-01） | `GET /api/chair/search/condition` → `GET /api/chair/search`（ページ移動で再取得）→ `GET /api/chair/:id` | `POST /api/chair/buy/:id` |
| おすすめ物件（US-02） | `GET /api/chair/:id` → `GET /api/recommended_estate/:id` → `GET /api/estate/:id` | `POST /api/estate/req_doc/:id` |
| 物件条件検索（US-03） | `GET /api/estate/search/condition` → `GET /api/estate/search`（条件変更時に再検索）→ `GET /api/estate/:id` | `POST /api/estate/req_doc/:id` |
| なぞって検索（US-04） | `POST /api/estate/nazotte` → マーカー選択 → `GET /api/estate/:id` | `POST /api/estate/req_doc/:id` |
| 最安イス（US-05） | `GET /api/chair/low_priced` → `GET /api/chair/:id`。詳細ではおすすめ物件取得もある。 | `POST /api/chair/buy/:id` |
| 最安物件（US-06） | `GET /api/estate/low_priced` → `GET /api/estate/:id` | `POST /api/estate/req_doc/:id` |

トップは最安イス・最安物件の両方を取得する。表は各利用経路に直接関係する処理を中心に記載し、全通信を列挙したものではない。

### 加点対象の実装

手元の実装では、購入（`POST /api/chair/buy/:id`）は在庫が正のイスを行ロックして在庫を1減らし、コミット後に200を返す。在庫切れ・対象なしの場合は404となる。資料請求（`POST /api/estate/req_doc/:id`）はメールが文字列であることと物件の存在を確認して200を返し、このハンドラー内にはメール送信や請求履歴保存の処理はない。したがって成功判定はメール到達ではなくAPI成功応答である。サーバー上の実装一致とDB更新前後は未検証。

なぞって検索のローカルUIは、描いた軌跡から**凸包**を作ってAPIへ送る。利用者の「囲った範囲」とAPIが受け取る多角形を対応づける際の注意点となる。今回の操作では頂点列や境界の正しさまでは検証していない。

## 途中で起きることと加点の関係

| 分岐 | 観測した事実 | 加点との関係 |
|---|---|---|
| 希望条件を追加して候補がなくなる | 家賃〜50000円＋エアコン付き＋ネット無料では2件。バス・トイレ別を追加するとカードが消え、解除すると元の2件に戻った。 | 結果なし自体を障害とは扱わない。条件調整後に資料請求まで進んで初めて加点対象に到達する。 |
| メールの形式を間違える | `not-an-email` は `Invalid email address format.`。有効な形式に修正すると200。 | ローカルUI実装ではAPI送信前に止まる。APIの誤応答による減点とは別。修正後の請求成功が加点に対応。 |
| 地図で候補を見つける | ドラッグ後にマーカーが現れ、クリックすると物件名リンクを表示。そこから詳細へ進めた。 | なぞって検索やマーカー表示には直接加点なし。最終的な資料請求が対象。 |
| 最安一覧から直接選ぶ | 検索フォームを経由せず、購入・請求とも成功。 | 条件検索を行うこと自体は、画面での購入・請求の必須条件ではない。 |

CSV入稿はマニュアルに記載されるデータ供給処理で、今回は未実行。直接加点の2種類には含まれないが、失敗・タイムアウトは致命的エラーとなる。botアクセスはコンバージョンにつながらず、仕様に合うUser-Agentへ503を返すことが許可されている。

## 性能調査へつなげる観点

- 購入・資料請求の完了件数を増やすのが目的。検索・ページング・おすすめ取得が遅い場合、利用者が成功地点まで到達する流れを妨げる可能性がある。これは経路からの推論で、ブラウザ操作だけではボトルネックを特定できない。
- イス詳細は購入と物件資料請求の両方への分岐点。詳細取得とおすすめ取得は、性能調査の対象候補となる。
- 条件検索は1利用者が複数回繰り返しうる。単純な「検索1回→請求1回」だけでなく、条件変更と再検索が成功前に増える経路がある。
- なぞって検索は結果取得後もマーカー・リンクの操作を挟む。地図の表示だけを成功とせず、資料請求まで到達できることを確認する。
- 最安一覧は条件入力のない入口。条件検索経路と合わせて、それぞれから最終成功へ進める状態を維持する必要がある。
- 在庫更新の整合性を保つ必要がある。検索で見えたイスでも、購入時点の在庫切れという分岐は別途検証対象。
- HTTPステータス・レスポンス内容の誤りは1回50点減点、10回以上で失格。成功数だけでなく正しさも必要。CSV入稿以外のタイムアウトは直接減点されないが、完了件数の機会を失う。

上記はブラウザ観測からの調査候補であり、実測ボトルネックや改善効果ではない。ベンチはAPIのみを呼ぶため、画面操作回数や地図タイルの読み込みをそのままベンチ負荷に置き換えない。ベンチが上記の経路をそのまま同じ順序でたどると断定はしない。
