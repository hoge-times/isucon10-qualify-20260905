**アプリの概要**(2〜3行): ISUUMO は「イスに似合う不動産を検索できる」サービス。イスを購入する利用と、転居先の物件資料を請求する利用があり、イス詳細のおすすめ物件が両者をつなぐ。

イス購入に至る2経路、物件の資料請求に至る4経路の計6経路をブラウザで実行し、購入2回・資料請求4回のすべてで画面に `200` が表示された。直接加点に対応するのは、検索の成功ではなく、この購入・資料請求の送信成功である。あわせて「検索結果がなくなったら条件を緩める」「メール入力を修正して再送する」という復帰の流れも確認した。

## 1. 仕様と採点

出典(マニュアルのファイル名と節)を添える。

- 採点式: `スコア = (イスの購入件数 + 物件の資料請求件数) - 減点`(`isucon10_qualify_manual.md`「スコア計算」)
- 加点対象の動作(何が成功すると点が入るか): イスの購入成功と物件の資料請求成功の2種類のみ。検索・ページング・詳細表示・おすすめ表示・地図操作には直接の加点はない(同「スコア計算」。画面側の内訳は章3)
- 減点・失格条件: HTTP ステータスコードやレスポンス内容の誤りは1回で50点減点、10回以上で失格。致命的なエラー(例: イス・物件の CSV 入稿の失敗・タイムアウト)は1回で失格。減点でスコアが0未満になると失格。`POST /initialize` が30秒以内に返らない、アプリケーション互換性チェックの失敗も失格。CSV 入稿以外の API でのタイムアウトによる失格・減点はない(同「スコア計算」「制約事項」)
- ベンチが叩く範囲と叩かない範囲(静的ファイル / HTML / 画像など): 「ベンチマークからのリクエストは、API に対してのみ行われます」「画像や HTML などの静的ファイルに対するリクエストは行われません」(同「3. 負荷走行 (ベンチマーク)」)。bot アクセスはコンバージョンに繋がらないため、bot の User-Agent(`/ISUCONbot(-Mobile)?/` ほか)に `503 Service Unavailable` を返すことは許可されており減点されない(同「bot からのリクエスト」)
- ブラウザ操作とベンチ負荷の差(追試でブラウザ表示が見られるか): 追試で「アプリケーションはブラウザ上での表示を初期状態と同様に保つ必要があります」と明記されており、ブラウザ表示は確認対象(同「制約事項」)。ブラウザ操作は HTML・画像・地図タイルの取得を伴うがベンチはそれを叩かない。「ベンチマーカーとブラウザの挙動に差異がある場合、ベンチマーカーの挙動を正とします」(同「競技内容」)

### 3.1 加点地点の実装照合

- ★ `POST /api/chair/buy/:id`(`go/main.go:533`): 在庫が正のイスを行ロックして在庫を1減らし、コミット後に200を返す。在庫切れ・対象なしの場合は404(trial-01 の V02)。
- ★ `POST /api/estate/req_doc/:id`(`go/main.go:908`): メールが文字列であることと物件の存在を確認して200を返し、このハンドラー内にはメール送信や請求履歴保存の処理はない。したがって成功判定はメール到達ではなく API の成功応答である(trial-01 の V02)。
- `POST /api/estate/nazotte`(`frontend/src/components/NazotteMap.tsx`。行は未特定): なぞって検索のローカル UI は、描いた軌跡から**凸包**を作って API へ送る。利用者の「囲った範囲」と API が受け取る多角形を対応づける際の注意点になる。今回の操作では頂点列や境界の正しさまでは検証していない(trial-02 の参照記録)。
- 成功表示全般(`frontend/src/pages/chair/detail/index.tsx`、`frontend/src/pages/estate/detail/index.tsx`。行は未特定): 画面の `200` は、frontend のハンドラーが API 応答の `response.status` と本文をそのまま表示していることから、API の成功応答と解釈している(trial-01 の V01)。サーバー上の実装一致と DB 更新前後は未検証。

### 6.1 性能調査へつなげる観点

経路からの**推論**であり実測ではない。`isucon-app-map` の章11 が読む。

- 加点地点の手前で繰り返し叩かれるエンドポイント(検索の再実行、ページ移動): 購入・資料請求の完了件数を増やすのが目的であり、検索・ページング・おすすめ取得が遅い場合は利用者が成功地点まで到達する流れを妨げる可能性がある。条件検索は1利用者が複数回繰り返しうる(US-03 は検索を3回行った)ため、単純な「検索1回→請求1回」だけでなく条件変更と再検索が成功前に増える経路もある。
- 複数の US が通る分岐点のエンドポイント(詳細画面など): イス詳細は購入と物件資料請求の両方への分岐点。詳細取得とおすすめ取得は性能調査の対象候補。
- 加点地点そのものの整合性(在庫、重複送信): 在庫更新の整合性を保つ必要がある。検索で見えたイスでも、購入時点の在庫切れという分岐は別途検証対象。HTTP ステータス・レスポンス内容の誤りは1回50点減点、10回以上で失格であり、成功数だけでなく正しさも必要(CSV 入稿以外のタイムアウトは直接減点されないが完了件数の機会を失う)。
- なぞって検索は結果取得後もマーカー・リンクの操作を挟む。地図の表示だけを成功とせず、資料請求まで到達できることを確認する。
- 最安一覧は条件入力のない入口。条件検索経路と合わせて、それぞれから最終成功へ進める状態を維持する必要がある。
- 上記はブラウザ観測からの調査候補であり、実測ボトルネックや改善効果ではない。ベンチは API のみを呼ぶため、画面操作回数や地図タイルの読み込みをそのままベンチ負荷に置き換えない。ベンチが上記の経路をそのまま同じ順序でたどると断定はしない。

**手動成功 6 件(購入2件＋資料請求4件)は実測のスコア増分ではない。** 採点式に当てると「ベンチで同種の成功が計上され、減点が増えなければ 6 点相当」にとどまる。**手動操作でスコアが6点増加したという測定結果ではない。**
