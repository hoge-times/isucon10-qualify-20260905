# ISUUMO：追加4経路と、つまずきからの復帰

2026-09-05 / [対象の練習環境](http://54.168.109.155/)

**前回未実行だった物件条件検索・なぞって検索・最安イス・最安物件の4経路を実行し、購入1回・資料請求3回で200表示を確認した。** さらに「検索結果がなくなったら条件を緩める」「メール入力を修正して再送する」という復帰の流れも確認した。

## 追加したユーザーストーリー

| ID | 利用者の目的 | 実行した経路 | 成功対象 |
|---|---|---|---|
| US-03 | 在宅勤務用に、5万円まででエアコンと無料ネットがある住まいを探したい。希望を満たす物件がなければ条件を緩めたい。 | 物件検索 → 賃料と特徴2つ → 2件 → 特徴を追加して結果なし → 追加条件を解除 → 安い方の詳細 → 資料請求 | 伊藤 ISUビル、ID6868、45672円。200表示。 |
| US-04 | 住所名だけでなく、地図上の住みたい範囲から物件を見つけたい。 | なぞって検索 → モード切替 → ドラッグ → マーカー → ポップアップの物件名 → 詳細 → 資料請求 | ISU高橋レジデンス、ID24964、93933円。200表示。 |
| US-05 | 細かな条件を入力せず、安いイスをすぐ買いたい。 | トップの最安イス → 詳細 → 購入 | 【お買い得】モダンなダイニングチェア、ID10831、1000円。200表示。 |
| US-06 | 家賃を優先して候補を見つけ、まず資料を取り寄せたい。 | トップの最安物件 → 詳細 → 資料請求 | 松本 ISUビル、ID7087、30001円。200表示。 |

これで前回分と合わせ、イス購入に至る2経路、物件資料請求に至る4経路をブラウザで確認できた。これは人がたどれる利用経路の分類であり、ベンチマーカーのシナリオ数を示すものではない。

## 途中で起きることと加点の関係

| 分岐 | 観測した事実 | 加点との関係 |
|---|---|---|
| 希望条件を追加して候補がなくなる | 家賃〜50000円＋エアコン付き＋ネット無料では2件。バス・トイレ別を追加するとカードが消え、解除すると元の2件に戻った。 | 結果なし自体を障害とは扱わない。条件調整後に資料請求まで進んで初めて加点対象に到達する。 |
| メールの形式を間違える | `not-an-email` は `Invalid email address format.`。有効な形式に修正すると200。 | ローカルUI実装ではAPI送信前に止まる。APIの誤応答による減点とは別。修正後の請求成功が加点に対応。 |
| 地図で候補を見つける | ドラッグ後にマーカーが現れ、クリックすると物件名リンクを表示。そこから詳細へ進めた。 | なぞって検索やマーカー表示には直接加点なし。最終的な資料請求が対象。 |
| 最安一覧から直接選ぶ | 検索フォームを経由せず、購入・請求とも成功。 | 条件検索を行うこと自体は、画面での購入・請求の必須条件ではない。 |

条件検索の2件は48347円→45672円の順だったため、今回の結果は価格昇順ではなかった。「検索結果の先頭＝最安」とは判断できず、最安一覧と条件検索は利用上の役割が異なる。

## APIへの対応（ローカル実装を参照）

| 経路 | 加点前の主な処理 | 加点対象の処理 |
|---|---|---|
| 物件条件検索 | `GET /api/estate/search/condition` → `GET /api/estate/search`（条件変更時に再検索）→ `GET /api/estate/:id` | `POST /api/estate/req_doc/:id` |
| なぞって検索 | `POST /api/estate/nazotte` → マーカー選択 → `GET /api/estate/:id` | `POST /api/estate/req_doc/:id` |
| 最安イス | `GET /api/chair/low_priced` → `GET /api/chair/:id`。詳細ではおすすめ物件取得もある。 | `POST /api/chair/buy/:id` |
| 最安物件 | `GET /api/estate/low_priced` → `GET /api/estate/:id` | `POST /api/estate/req_doc/:id` |

トップは最安イス・最安物件の両方を取得する。表は各利用経路に直接関係する処理を中心に記載し、全通信を列挙したものではない。

なぞって検索のローカルUIは、描いた軌跡から**凸包**を作ってAPIへ送る。利用者の「囲った範囲」とAPIが受け取る多角形を対応づける際の注意点となる。今回の操作では頂点列や境界の正しさまでは検証していない。

## 次の性能調査へつなげる観点

- 条件検索は1利用者が複数回繰り返しうる。単純な「検索1回→請求1回」だけでなく、条件変更と再検索が成功前に増える経路がある。
- なぞって検索は結果取得後もマーカー・リンクの操作を挟む。地図の表示だけを成功とせず、資料請求まで到達できることを確認する。
- 最安一覧は条件入力のない入口。条件検索経路と合わせて、それぞれから最終成功へ進める状態を維持する必要がある。

上記はブラウザ観測からの調査候補であり、実測ボトルネックや改善効果ではない。ベンチはAPIのみを呼ぶため、画面操作回数や地図タイルの読み込みをそのままベンチ負荷に置き換えない。

## スコアと検証範囲

採点式は購入件数＋資料請求件数−減点。今回の成功4件は、ベンチ走行中に同種の成功が計上され減点が増えなければ4点相当だが、**手動操作でスコアが4点増加したという測定結果ではない**。

在庫切れ、同時購入、CSV入稿、bot、地図の境界・空結果・大範囲、ベンチの経路選択確率は未検証。ブラウザの要素指定が一度失敗したが、最新の画面情報から選び直して成功した。これは操作ツール側の失敗としてログに残し、アプリのタイムアウトや減点には数えていない。
