# ISUUMO：ブラウザで確かめたユーザーストーリーと加点動作

2026-09-05 / 対象：[練習環境](http://54.168.109.155/)

**条件検索からのイス購入と、イスにおすすめの物件への資料請求を各1回実行し、両方で画面に200が表示された。直接加点に対応するのは、検索の成功ではなく、この2つの送信成功である。**

ブラウザでの手動操作はベンチマーカーのスコア計測ではない。今回「スコアが2点上がった」とは報告できない。採点仕様上、ベンチ走行中に購入1件・資料請求1件が正常に計上され、減点が増えなければ、合計2点に相当する。

## 仕様の理解

ISUUMOは「イスに似合う不動産を検索できる」サービス。イスを購入する利用と、転居先の物件資料を請求する利用があり、イス詳細のおすすめ物件が両者をつなぐ。

マニュアルの採点式は `スコア = (イスの購入件数 + 物件の資料請求件数) - 減点`。ベンチはAPIのみを呼び、HTML・画像の取得は行わない。ただしブラウザ表示は追試対象となる。

## 実施した2通り

| ID | ユーザーストーリー | 実際に通った流れ | 成功・加点地点 |
|---|---|---|---|
| US-01 | 在宅作業用のイスを探す利用者として、3000円までの黒いゲーミングチェアを比較して購入したい。 | トップ → イス検索 → 価格・色・種類を指定 → 検索 → 2ページ目 → イス詳細 → メール入力 → Submit | イスID `10169` の購入で画面に200。ベンチでの購入成功1件に対応。 |
| US-02 | 気に入ったイスを置く住まいを探す利用者として、そのイスにおすすめの物件を確認し、検討用の資料を請求したい。 | US-01のイス詳細 → おすすめ物件一覧 → 「坂本 ISUマンション」 → 物件詳細 → メール入力 → Submit | 物件ID `7045` の資料請求で画面に200。ベンチでの資料請求成功1件に対応。 |

US-01で選んだ「【本格仕様】金のダイニングチェア」は1089円・黒・ゲーミングチェア。名前ではなく詳細の種類欄で検索条件との一致を確認した。検索結果はページを送ると別の候補に変わった。

US-02の物件は家賃34844円、ドア縦87cm・横193cm。推薦は購入前から表示されており、「購入しないと物件を探せない」という制約は画面にはなかった。推薦条件の厳密な判定規則は今回検証していない。

## 動作とAPIの対応

API名は手元のfrontend・Go実装から照合したもの。実ブラウザのネットワークログを採取した結果ではない。

| 動作 | 対応API | スコアとの関係 |
|---|---|---|
| トップの安いイス・物件を表示 | `GET /api/chair/low_priced`、`GET /api/estate/low_priced` | 直接加点なし。購入・資料請求へ誘導する入口。 |
| イス検索条件を取得 | `GET /api/chair/search/condition` | 直接加点なし。検索の前提。 |
| 絞り込み検索・ページ移動 | `GET /api/chair/search` | 直接加点なし。購入対象を見つける処理。 |
| イス詳細を表示 | `GET /api/chair/:id` | 直接加点なし。対象確認。 |
| おすすめ物件を表示 | `GET /api/recommended_estate/:id` | 直接加点なし。物件の資料請求への経路。 |
| **イス購入を送信** | **`POST /api/chair/buy/10169`** | **購入件数に対応する成功地点。** |
| 物件詳細を表示 | `GET /api/estate/7045` | 直接加点なし。対象確認。 |
| **資料請求を送信** | **`POST /api/estate/req_doc/7045`** | **資料請求件数に対応する成功地点。** |

手元の実装では、購入は在庫が正のイスを行ロックして在庫を1減らし、コミット後に200を返す。在庫切れ・対象なしの場合は404となる。資料請求はメールが文字列であることと物件の存在を確認して200を返し、このハンドラー内にはメール送信や請求履歴保存の処理はない。したがって今回の成功判定はメール到達ではなくAPI成功応答である。サーバー上の実装一致とDB更新前後は未検証。

## スコア改善に向けた読み取り

- 購入・資料請求の完了件数を増やすのが目的。検索・ページング・おすすめ取得が遅い場合、利用者が成功地点まで到達する流れを妨げる可能性がある。これは経路からの推論で、今回の操作だけではボトルネックを特定できない。
- イス詳細は購入と物件資料請求の両方への分岐点。詳細取得とおすすめ取得は、次の性能調査の対象候補となる。
- 在庫更新の整合性を保つ必要がある。検索で見えたイスでも、購入時点の在庫切れという分岐は別途検証対象。
- HTTPステータス・レスポンス内容の誤りは1回50点減点、10回以上で失格。成功数だけでなく正しさも必要。CSV入稿以外のタイムアウトは直接減点されないが、完了件数の機会を失う。

今回は性能計測もベンチマーカーの実行順・分岐頻度の解析も行っていない。上記の経路をベンチがそのまま同じ順序でたどると断定はしない。
